17. Por qué existen las bases de datos no relacionales Evolución & Paradigma

El modelo relacional tradicional (SQL) sobresale en la garantía de integridad referencial, normalización formal, transacciones ACID estrictas y cruces mediante JOIN. Sin embargo, surgen fricciones críticas ante determinados requerimientos del desarrollo moderno:

  • Estructuras variables o polimórficas: Entidades cuyos atributos cambian dinámicamente según la categoría o subtipo. En SQL esto obliga a proliferar columnas nulas dispersas o recurrir al antipatrón EAV (Entity-Attribute-Value), complejizando el mantenimiento.
  • Desajuste de impedancia objeto-relacional: Los objetos del código suelen presentar estructuras anidadas naturales (listas, direcciones, propiedades compuestas). En el modelo relacional deben desensamblarse artificialmente en múltiples tablas normalizadas y recomponerse con múltiples joins en cada lectura.
  • Crecimiento y escalabilidad horizontal: Las bases relacionales escalan fundamentalmente de manera vertical (agregando más CPU y RAM a un único servidor). Las soluciones NoSQL fueron concebidas desde su arquitectura nativa para escalar horizontalmente (distribución de nodos en clústeres mediante particionamiento o sharding).
18. Las cuatro familias NoSQL Taxonomía de Motores

El universo no relacional clasifica sus tecnologías según el modelo de datos subyacente y el caso de uso óptimo:

1. Documentales (MongoDB, CouchDB, Firestore)

Almacenan información en documentos estructurados jerárquicos (JSON/BSON) que admiten anidamiento y esquemas flexibles. Ideales para catálogos comerciales, perfiles de usuario, bitácoras de auditoría y formularios dinámicos.

2. Clave-Valor (Redis, DynamoDB, Memcached)

Asocian un valor binario opaco a una clave única, operando primariamente en memoria RAM con tiempos de respuesta submilimétricos. Indicadas para sesiones distribuidas, memoria caché, tablas de clasificación y contadores.

3. Columnares / Column-Family (Cassandra, HBase)

Organizan los datos por columnas en lugar de filas, optimizando lecturas masivas y compresiones sobre volúmenes gigantescos distribuidos. Diseñadas para series temporales, telemetría IoT y analítica Big Data.

4. De Grafos (Neo4j, Amazon Neptune)

Estructuran nodos (entidades) interconectados por aristas (relaciones dirigidas tipificadas con propiedades). Especializadas en redes sociales, motores de recomendación, detección de fraudes y trazabilidad de rutas.

19. Modelo documental: documento, BSON, _id y colecciones Fundamentos en MongoDB

MongoDB modela el almacenamiento basándose en agrupaciones flexibles y formatos binarios optimizados:

  • Documento: Unidad básica de registro compuesta por pares clave-valor que admite estructuras jerárquicas embebidas (subdocumentos) y listas ordenadas (arreglos).
  • BSON (Binary JSON): Serialización binaria de JSON utilizada internamente por el motor. Agrega eficiencia de recorrido y tipos de datos que JSON no soporta nativamente: fechas exactas (Date), identificadores unívocos (ObjectId), números de punto flotante de alta precisión (Decimal128), enteros de 32/64 bits y flujos binarios (BinData).
  • Identificador _id y ObjectId: Todo documento exige un campo _id primario e inmutable. Si no es asignado por el usuario, el motor genera un ObjectId de 12 bytes compuesto por una marca de tiempo (timestamp de 4 bytes), un valor aleatorio de máquina/proceso (5 bytes) y un contador incremental (3 bytes), garantizando unicidad global sin coordinación central de red.
  • Equivalencias léxicas con el modelo relacional:
    Colección ≈ Tabla | Documento ≈ Fila/Registro | Campo ≈ Columna | Embeber / $lookup ≈ JOIN
20. Esquema flexible y validación de esquema Gobernanza de Datos

La propiedad de esquema flexible establece que documentos pertenecientes a la misma colección pueden presentar estructuras, nombres de campos y tipos de datos dispares entre sí.

  • Ventajas y riesgos: Acelera la iteración ágil y la evolución del código sin requerir migraciones bloqueantes (ALTER TABLE). No obstante, introduce el riesgo de inconsistencias graves, degradación de datos por errores tipográficos en nombres de campos o presencia de formatos incompatibles.
  • Validación con $jsonSchema: Regla formal que puede aplicarse al crear o modificar una colección (validator: { $jsonSchema: { ... } }). Permite imponer obligatoriedad de campos (required), validar tipos BSON (bsonType), restringir rangos numéricos y acotar valores mediante enumeraciones (enum).
  • Límite físico de 16 MB: Ningún documento BSON individual puede superar los 16 megabytes. Si una relación o subdocumento amenaza con exceder este umbral, el modelado impone desacoplar y referenciar en colecciones separadas.
21. Operaciones CRUD en mongosh Comandos del Shell

Sintaxis canónica para la manipulación directa de datos desde la consola de comandos de MongoDB:

  • Inserción: db.coleccion.insertOne({ ... }) para un solo documento y db.coleccion.insertMany([ { ... }, { ... } ]) para lotes. Si la base de datos o la colección no existen al momento de insertar, el motor las crea de forma automática.
  • Lectura: db.coleccion.find(filtro, proyeccion) y db.coleccion.findOne(filtro). La proyección delimita los campos devueltos mediante indicadores binarios (ej. { nombre: 1, email: 1, _id: 0 }). Admite encadenamiento de .sort({ fecha: -1 }) (ordenamiento), .skip(10) (desplazamiento) y .limit(10) (paginación).
  • Actualización: updateOne(filtro, actualizacion) y updateMany(filtro, actualizacion). Exigen operadores de mutación atómica: $set (modifica o añade campos), $inc (incrementa contadores), $push (agrega elementos a un arreglo) y $unset (remueve campos). El método replaceOne() reemplaza la totalidad del documento preservando únicamente el _id.
  • Eliminación: db.coleccion.deleteOne(filtro) y db.coleccion.deleteMany(filtro). Precaución: pasar un filtro vacío {} en deleteMany vacía la colección por completo.
22. Operadores de consulta e índices Optimización de Consultas

Mecanismos para filtrar y optimizar el rendimiento de recuperación sobre grandes volúmenes de documentos:

  • Operadores de comparación: $eq (igual), $ne (distinto), $gt/$gte (mayor / mayor o igual), $lt/$lte (menor / menor o igual), $in (dentro de una lista de valores) y $nin (no contenido).
  • Operadores lógicos y de evaluación: $and, $or, $not, $nor; operadores de existencia y tipo como $exists: true y $type; y coincidencias por patrones mediante expresiones regulares ($regex).
  • Consultas en arreglos: $all (debe contener todos los elementos indicados), $size (longitud exacta) y $elemMatch (condición compuesta sobre elementos de un subdocumento en arreglo).
  • Índices (B-Tree): Estructuras auxiliares creadas con db.coleccion.createIndex({ campo: 1 }) que evitan el escaneo secuencial de toda la colección (COLLSCAN), transformándolo en una búsqueda indexada eficiente (IXSCAN). En índices compuestos el orden de los campos es determinante (regla de igualdad primero, luego ordenamiento y rango).
  • Diagnóstico con explain('executionStats'): Herramienta de auditoría analítica que expone las métricas del planificador: cantidad de documentos examinados (totalDocsExamined) frente a documentos devueltos (nReturned).
23. Modelado documental: embeber o referenciar Decisión Arquitectónica Central

Dilema fundamental del diseño en bases de datos orientadas a documentos:

Embeber (Documentos Anidados):
El dato secundario vive dentro del documento raíz. Ventaja: recuperación en una única lectura sin joins y modificaciones atómicas. Desventaja: riesgo de duplicación de datos y de colisión contra el límite de 16 MB.
Referenciar (Vínculo por Clave):
El dato reside en una colección independiente vinculada mediante el _id. Ventaja: previene el crecimiento desmedido y elimina la duplicación. Desventaja: exige múltiples consultas o el uso de la etapa agregada $lookup.
Reglas prácticas de decisión según cardinalidad:
  • Uno a pocos (1:few): Embeber directamente (ej. direcciones de un usuario o números de teléfono).
  • Uno a muchos acotado (1:many): Embeber si la lista tiene un límite previsible; de lo contrario, referenciar.
  • Uno a muchísimos (1:squillions): Referenciar obligatoriamente (ej. logs de un servidor o transacciones de un sensor).
  • Muchos a muchos (N:M): Referenciar mediante colecciones separadas, o embeber únicamente en el documento del lado que se consulta con mayor frecuencia.
  • Datos históricos congelados: Si el dato no debe modificarse cuando cambie el maestro (ej. precio unitario o descripción del producto al momento de emitir una factura), debe embeberse para preservar la foto histórica.
24. Cuándo conviene MongoDB y la arquitectura híbrida Criterio de Selección Tecnológica

La elección entre una base relacional y un motor documental debe fundarse en las restricciones del dominio:

  • Conviene usar MongoDB cuando: La estructura de las entidades es variable, se consulta predominantemente el documento completo en una sola operación, existen jerarquías naturales anidadas, se necesita prototipar a alta velocidad, o se implementan módulos de auditoría, eventos, catálogos y sistemas de alto volumen con escalabilidad horizontal.
  • Conviene mantener una base Relacional cuando: El esquema es rígido y altamente estable, la lógica de negocio depende de transacciones ACID distribuidas sobre múltiples tablas críticas (facturación, contabilidad, reservas bancarias), o el sistema depende de complejas herramientas de Business Intelligence y reportes analíticos SQL consolidados.
  • Arquitectura Híbrida (Políglota): Enfoque moderno donde conviven ambos motores sin necesidad de migrar la totalidad del sistema. Se conserva una base de datos relacional (ej. PostgreSQL) para el núcleo transaccional financiero y se integra MongoDB para módulos complementarios de alto dinamismo (historiales de auditoría, catálogo de atributos variables o notificaciones).

Eje 5 · Almacenamiento de Archivos

Metadatos, estrategias de almacenamiento, Object Storage (S3/MinIO), consistencia en patrones híbridos y seguridad.

33. El archivo como dato particular y sus metadatos Naturaleza & Atributos

Un archivo informático no puede gestionarse como un dato convencional (texto, números o fechas). Posee una naturaleza volumétrica extensa, es binario, no se indexa ni consulta por su contenido directo y se transfiere de forma secuencial por streaming:

  • Impacto sistémico: Manipular binarios directamente sobre el motor de base de datos degrada el rendimiento de la memoria caché, satura el pool de conexiones y multiplica exponencialmente el tamaño de los respaldos (backups).
  • Persistencia de metadatos: Independientemente de dónde resida el binario, la base de datos debe almacenar formalmente sus descriptores estructurales:
    • Nombre original enviado por el cliente (para preservar la semántica del usuario).
    • Nombre o clave interna única generada por el sistema (UUID).
    • Tipo MIME verificado (ej. application/pdf, image/webp).
    • Tamaño exacto del archivo en bytes.
    • Fecha y hora de carga.
    • Entidad o usuario propietario responsable.
    • Ubicación lógica (identificador del bucket, clave o ruta relativa).
  • Ventaja operativa: Permite consultar, ordenar, paginar y evaluar autorizaciones de descarga sin necesidad de abrir ni transferir el archivo binario real.
34. Estrategias para almacenar archivos Comparativa de Arquitecturas

Existen tres aproximaciones para resolver la persistencia de binarios en sistemas de software:

Estrategia Ubicación del Binario Ubicación de Metadatos Diagnóstico en Entornos Cloud
En Base de Datos Campos BLOB / bytea / GridFS En la misma fila/documento Sobrecarga copias de seguridad y memoria RAM; justificado solo en volúmenes pequeños con transaccionalidad estricta.
En Disco del Servidor Sistema de archivos local (filesystem) Ruta relativa en la base de datos Inviable en la nube: los sistemas PaaS (Render, Railway, Heroku) operan con discos efímeros que borran archivos en cada reinicio, y las instancias escaladas no comparten almacenamiento local.
Object Storage Servicio externo (S3, R2, MinIO) Clave del objeto en la base de datos Estándar de la industria: almacenamiento ilimitado, alta disponibilidad, distribución geográfica y desacoplamiento total del backend.
35. Binarios en la base de datos relacional Tipos BLOB & JPA

Persistencia directa de secuencias de bytes dentro de motores relacionales:

  • Tipos nativos por motor: bytea en PostgreSQL; TINYBLOB, BLOB, MEDIUMBLOB y LONGBLOB (hasta 4 GB) en MySQL; VARBINARY(MAX) en SQL Server.
  • Mapeo mediante JPA: Se utiliza el tipo byte[] anotado con @Lob (Large Object).
  • Buenas prácticas obligatorias:
    • Separar el arreglo binario en una entidad secundaria vinculada (@OneToOne), evitando que las consultas generales sobre el registro carguen los megabytes del archivo a la memoria.
    • Configurar la relación con FetchType.LAZY para transferir los bytes únicamente bajo demanda explícita.
    • Utilizar streaming en el controlador mediante StreamingResponseBody o flujos InputStream para evitar el agotamiento de memoria del servidor al servir descargas.
  • Criterio de aplicación: Recomendable exclusivamente para sistemas cerrados con bajo volumen de archivos pequeños (ej. firmas digitales o sellos notariales) donde la transaccionalidad atómica indivisible con el registro sea un requisito excluyente.
36. Archivos en MongoDB: BinData y GridFS BinData vs. GridFS

Mecanismos provistos por el motor documental para la persistencia binaria:

Tipo BinData (En documento):
El archivo se almacena como un campo binario nativo dentro del documento BSON. Aplica únicamente a archivos pequeños (iconos, avatares o thumbnails), ya que el archivo sumado al resto de los campos de la entidad no puede superar el límite estricto de 16 MB por documento.
Especificación GridFS (Chunky Storage):
Especializado para archivos que exceden los 16 MB. Segmenta el binario en fragmentos contiguos (chunks de 255 KB por defecto) y los administra automáticamente mediante dos colecciones acopladas: fs.files (metadatos generales) y fs.chunks (fragmentos binarios con índice de orden). Permite lectura y escritura por streaming sin cargar el archivo completo en memoria.
37. Object storage: Amazon S3 y compatibles Estándar S3 & Buckets

Paradigma de almacenamiento optimizado para la nube donde los datos se administran como objetos autónomos en lugar de bloques de disco o jerarquías de archivos:

  • Anatomía del objeto: Constituido por el flujo binario, un identificador de clave única (Object Key) y metadatos extensibles. Se alojan en contenedores raíz llamados Buckets. No existe un concepto real de carpetas en el sistema de almacenamiento; los prefijos en la clave (ej. usuarios/12/foto.jpg) son cadenas de texto planas que las interfaces visuales interpretan como carpetas lógicas.
  • Ecosistema API de S3: La interfaz de Amazon S3 se convirtió en el estándar de facto del mercado. Motores de código abierto como MinIO y proveedores en la nube como Cloudflare R2 o Backblaze B2 implementan la misma especificación, permitiendo utilizar el cliente oficial de AWS SDK en Spring Boot sin modificar una sola línea de código, variando únicamente el endpoint, credenciales y región.
  • Seguridad de buckets: Por directiva canónica de seguridad, los buckets deben permanecer estrictamente privados (bloqueo total de acceso público), autorizando la lectura o carga mediante credenciales de servicio o URLs prefirmadas.
38. Subida por backend (proxy) vs URL prefirmada Flujos de Transferencia
1. Subida vía Backend (Proxy)

El cliente envía el archivo como multipart/form-data a la API de Spring Boot. El backend lo recibe, valida el tamaño y tipo en memoria/disco temporal, lo sube al bucket S3 y finalmente registra los metadatos en la base de datos.

  • Ventaja: Simple de implementar, control absoluto y validación previa estricta.
  • Desventaja: Satura el ancho de banda del servidor, bloquea hilos de ejecución de la API y consume memoria RAM de forma crítica ante cargas concurrentes.
2. Subida con URL Prefirmada (Presigned URL)

El cliente solicita autorización a la API. El backend valida permisos y genera una URL temporal firmada criptográficamente con expiración breve (ej. 15 minutos). El cliente sube el binario directamente desde el navegador al bucket vía PUT HTTP, y luego notifica al backend para asentar el registro.

  • Ventaja: Descarga todo el tráfico del backend y escala masivamente.
  • Desventaja: Exige configurar políticas CORS en el bucket y realizar validaciones reactivas posteriores.
39. Patrón híbrido y consistencia entre base y almacenamiento Tolerancia a Fallas

Al implementar el patrón híbrido (metadatos en base de datos y binarios en Object Storage), las dos operaciones de escritura no participan de una misma transacción ACID distribuida. Esto puede originar fallas de consistencia que deben ser mitigadas:

  • Objeto Huérfano: Ocurre si el archivo se sube exitosamente al Object Storage pero la sentencia INSERT de la base de datos falla por validación o error de red. Mitigación: Implementar tareas programadas en segundo plano (cron jobs) que comparen el inventario del bucket contra los registros de la base y eliminen objetos huérfanos que superen las 24 horas de antigüedad.
  • Enlace Roto (Broken Reference): Ocurre si se asienta el registro en la base de datos pero la subida del binario falla. Mitigación: Respetar siempre el orden seguro (subir primero el archivo al almacenamiento y registrar los metadatos solo tras confirmar el código HTTP 200 de subida, o verificar la existencia del binario mediante la operación headObject).
  • Limpieza de bajas: Si se elimina un registro de la base pero falla el borrado en el bucket, el costo de almacenamiento persiste. Se recomienda emplear borrado lógico en la entidad y diferir la eliminación física del binario a un proceso de limpieza por lotes.
40. Seguridad en la carga de archivos Protección & Directivas

La carga de archivos representa uno de los vectores de ataque más críticos (RCE, DoS, Path Traversal). Deben aplicarse medidas de seguridad estrictas:

  • Nunca confiar en los datos del cliente: El nombre del archivo, la extensión y la cabecera Content-Type son suministrados por el navegador y pueden ser fácilmente falsificados por un atacante (ej. renombrar un archivo ejecutable .exe o .php a .jpg).
  • Detección de números mágicos (Magic Numbers): Inspeccionar los primeros bytes del encabezado binario del archivo (utilizando librerías como Apache Tika) para determinar su tipo MIME real e intrínseco, contrastándolo contra una lista blanca estricta de formatos permitidos.
  • Generación de nombres únicos (UUID): Jamás utilizar el nombre original del archivo para guardarlo en el disco o en el bucket. Se debe generar un identificador unívoco aleatorio (ej. UUID.randomUUID()), previniendo ataques de escape de directorios (Path Traversal: ../../etc/passwd) y colisiones accidentales de nombres entre usuarios.
  • Autorización en descargas y vectores especiales: La descarga de archivos privados debe validar que el usuario autenticado tenga permisos específicos sobre ese recurso en particular. Además, deben aplicarse límites rígidos de tamaño de subida, restringir archivos con riesgo de scripts incrustados (como imágenes SVG con código JavaScript) y deshabilitar la descompresión recursiva automática para evitar ataques de denegación de servicio por bombas de descompresión (Zip Bombs).

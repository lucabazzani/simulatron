Eje 2 · Backend con Java Spring Boot

Arquitectura en capas, persistencia JPA, diseño de APIs RESTful, validación y seguridad stateless.

9. Arquitectura en capas Controller–Service–Repository Patrones & Responsabilidades

Estructuración arquitectónica basada en el principio de responsabilidad única (SRP), que desacopla el ciclo de vida de una petición HTTP en estratos especializados:

  • Capa Controlador (@RestController): Puerta de entrada del sistema. Responsable exclusivo del protocolo HTTP: deserializa la carga útil, dispara la validación estructural de entrada, delega la ejecución al servicio y empaqueta la respuesta final en un contenedor ResponseEntity. No debe contener lógica de negocio ni comunicarse directamente con la base de datos.
  • Capa de Servicio (@Service): Núcleo operativo del backend. Implementa las reglas del dominio, orquesta transacciones mediante @Transactional, coordina múltiples repositorios y efectúa el mapeo bidireccional entre DTOs y Entidades.
  • Capa de Repositorio (@Repository): Capa de acceso a datos que encapsula las operaciones de lectura y persistencia a través de la interfaz de Spring Data JPA.
  • Modelos de datos: La Entidad modela el esquema relacional persistente, mientras que el DTO define formalmente el contrato de transferencia con los clientes de la API.
10. Inyección de dependencias y estereotipos de Spring Inversión de Control (IoC)

El contenedor de inversión de control (IoC) de Spring gestiona el ciclo de vida, configuración e instanciación de los componentes de la aplicación (Beans), entregándolos a las clases consumidoras para reducir el acoplamiento y favorecer la testabilidad.

  • Anotaciones de estereotipo: Especializaciones semánticas de @Component que registran clases en el contexto de Spring: @Service (lógica del dominio), @Repository (persistencia y traducción de excepciones SQL) y @RestController (controlador web con serialización JSON implícita).
  • Anotación @SpringBootApplication: Agrupador canónico que unifica @Configuration (definición de beans programáticos), @EnableAutoConfiguration (carga de dependencias según el classpath) y @ComponentScan (escaneo reflexivo de paquetes desde la clase raíz).
  • Inyección por constructor: Práctica recomendada sobre la inyección por campo (@Autowired directo). Combinada con modificadores final (o @RequiredArgsConstructor de Lombok), asegura inmutabilidad, previene punteros nulos durante la inicialización y permite instanciar servicios en pruebas unitarias puras sin levantar el contexto completo de Spring.
11. Entidades JPA y mapeo objeto-relacional Persistencia & ORM

Mecanismo que traduce clases Java orientadas a objetos en tablas relacionales de base de datos a través de la especificación JPA y el motor Hibernate:

  • Mapeo estructural: @Entity declara la persistencia, @Table define el nombre físico, @Id establece la clave primaria vinculada con @GeneratedValue(strategy = GenerationType.IDENTITY), y @Column tipifica las restricciones del campo.
  • Relaciones relacionales: Asociaciones @ManyToOne, @OneToMany, @OneToOne y @ManyToMany. El lado dueño declara la columna de clave foránea mediante @JoinColumn, mientras que el lado inverso utiliza el atributo mappedBy para evitar redundancias de esquemas.
  • Estrategias de carga (FetchType):
    • FetchType.LAZY (Diferida): Carga las relaciones únicamente cuando son invocadas explícitamente en el código. Es la opción recomendada para prevenir el grave problema de rendimiento de consultas N+1.
    • FetchType.EAGER (Inmediata): Ejecuta joins o subconsultas automáticas para traer todas las relaciones asociadas junto con la entidad principal, saturando memoria de forma prematura.
12. Spring Data JPA: repositorios, query methods y paginación Acceso a Datos & Rendimiento

Capa de abstracción que elimina la necesidad de escribir implementaciones manuales de acceso a datos mediante la extensión de la interfaz genérica JpaRepository<Entidad, TipoId>:

  • Operaciones provistas: Métodos estándar listos para producción (save, findById, findAll, deleteById, count y existsById).
  • Métodos de consulta derivados (Query Methods): Generación automatizada de consultas SQL complejas a partir de la signatura léxica del método en la interfaz (ej. findByEmail(String email) o findByActivoTrueAndNombreContainingIgnoreCase(String nombre)).
  • Consultas explícitas (@Query): Declaración de sentencias JPQL (orientadas al modelo de objetos) o SQL nativas para consultas de alto volumen o joins complejos que no resultan prácticos mediante nombres de métodos.
  • Paginación obligatoria (Pageable y Page<T>): Evita el colapso por agotamiento de memoria del servidor (Out of Memory) y reduce el ancho de banda transferido al fragmentar listados en bloques acotados con soporte de ordenamiento nativo (Sort).
13. DTOs y validación de datos Contratos de API & Seguridad

Los Objetos de Transferencia de Datos (DTO) definen formalmente la estructura de entrada y salida de los endpoints, desacoplando los esquemas de base de datos de los clientes externos:

  • Riesgos de exponer entidades directamente: Puede filtrar atributos sensibles (contraseñas hasheadas, tokens, marcas internas de auditoría), genera acoplamiento rígido entre el cliente y las tablas, y desata errores de serialización JSON como referencias circulares infinitas o excepciones por sesiones cerradas en relaciones LAZY.
  • Especialización: Request DTO recibe exclusivamente la información requerida para la operación aplicando validaciones declarativas; Response DTO devuelve proyecciones sanitizadas.
  • Anotaciones de validación Jakarta: @NotNull (no nulo), @NotBlank (no vacío ni compuesto solo por espacios en blanco), @Size (longitudes mínimas/máximas), @Email (formato de correo), @Positive y @Pattern (expresiones regulares). Se activan en los controladores mediante la anotación @Valid en el parámetro del cuerpo.
14. Controladores REST, verbos y códigos HTTP Diseño de Interfaces Web

Implementación de interfaces orientadas a recursos siguiendo los principios arquitectónicos REST:

  • Semántica de verbos HTTP: GET para recuperación segura e idempotente, POST para creación de recursos subordinados, PUT para reemplazo total de estado, PATCH para modificaciones parciales y DELETE para remoción.
  • Mapeo de parámetros: Extracción de identificadores en rutas jerárquicas (@PathVariable), filtros o paginaciones en la cadena de consulta (@RequestParam) y desensamblado del cuerpo JSON entrante (@RequestBody).
  • Códigos de estado canónicos (ResponseEntity):
    • 200 OK: Operación exitosa con cuerpo de retorno.
    • 201 Created: Creación confirmada con cabecera de ubicación (Location).
    • 204 No Content: Ejecución exitosa sin cuerpo de retorno (común en bajas o actualizaciones).
    • 400 Bad Request: Error de validación o sintaxis mal formada.
    • 401 Unauthorized / 403 Forbidden: Ausencia de autenticación válida vs. permisos insuficientes sobre el recurso.
    • 404 Not Found: Recurso inexistente en el sistema.
    • 409 Conflict: Conflicto con el estado actual (ej. registros únicos duplicados).
15. Manejo global de excepciones Resiliencia & Respuestas Consistentes

Estrategia centralizada orientada a interceptar fallas operativas en cualquier capa de la aplicación, evitando la dispersión de bloques try/catch redundantes y la exposición accidental de trazas de pila (stack traces) al cliente.

  • Anotaciones arquitectónicas: Se utiliza una clase interceptora decorada con @RestControllerAdvice (o @ControllerAdvice), la cual contiene métodos específicos mapeados mediante @ExceptionHandler(TipoExcepcion.class).
  • Excepciones del dominio: Creación de excepciones personalizadas no chequeadas (ResourceNotFoundException, BusinessException) que portan significado semántico del negocio.
  • Estructura canónica de respuesta de error: Estándar uniforme en formato JSON que garantiza previsibilidad a los clientes frontend: 
    {
  "timestamp": "2026-11-06T20:30:00Z",
  "status": 404,
  "error": "Not Found",
  "message": "El recurso con ID 12 no existe en el sistema.",
  "path": "/api/v1/productos/12"
}
16. Seguridad stateless con Spring Security y JWT Autenticación & Autorización

Mecanismo de seguridad desacoplado para arquitecturas SPA/móviles donde el servidor no retiene sesiones en memoria (SessionCreationPolicy.STATELESS), permitiendo escalado horizontal inmediato.

  • Flujo de autenticación: El cliente envía credenciales vía POST /auth/login; el servicio valida contra la base con contraseñas hasheadas mediante BCryptPasswordEncoder y genera un JSON Web Token firmado criptográficamente que retorna al cliente.
  • Anatomía del Token (JWT): Compuesto por tres segmentos codificados en Base64Url separados por puntos: Header (algoritmo de firma), Payload (declaraciones/claims: emisor, sujeto, roles y fecha de expiración) y Signature (garantía criptográfica de integridad). El payload no está cifrado, por lo que nunca debe contener información confidencial.
  • Autorización en peticiones subsiguientes: Un filtro perimetral (OncePerRequestFilter) intercepta la cabecera Authorization: Bearer <token>, valida la firma y vigencia del token y establece el contexto de seguridad (SecurityContextHolder) para que anotaciones como @PreAuthorize("hasRole('ADMIN')") controlen el acceso a los métodos.
  • Control de CORS: Configuración explícita en el filtro de seguridad que autoriza los orígenes cruzados (dominios del frontend), métodos HTTP y encabezados permitidos por las políticas de seguridad del navegador.

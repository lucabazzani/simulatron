Eje 4 · Contenedores con Docker

Aislamiento de entornos, ciclo de vida de imágenes, Dockerfile multi-etapa, redes internas y orquestación con Compose.

25. Contenedores frente a máquinas virtuales Aislamiento & Virtualización

Los contenedores resuelven el histórico problema del «en mi máquina funciona», originado por discrepancias de versiones de software, librerías del sistema, variables no documentadas y dependencias divergentes entre los puestos de desarrollo y los servidores de producción:

  • Máquinas Virtuales (VM): Virtualizan el hardware completo a través de un hipervisor (Type 1 o Type 2). Cada máquina virtual exige la instalación y ejecución de un Sistema Operativo invitado (Guest OS) independiente con sus propios drivers, servicios en segundo plano y kernels redundantes. Demandan gigabytes de almacenamiento y minutos en iniciar.
  • Contenedores Docker: Virtualizan a nivel del Sistema Operativo. Comparten directamente el kernel del host anfitrión y aíslan los procesos de la aplicación mediante mecanismos nativos de Linux (namespaces para aislamiento de procesos/red y cgroups para limitación de recursos). Ocupan megabytes de disco y se inicializan en fracciones de segundo.
  • Reproducibilidad total: Empaquetan el código fuente compilado junto con su entorno exacto de ejecución, garantizando que el comportamiento sea idéntico en desarrollo, pruebas de integración y despliegue final.
26. Imagen, contenedor y registro Artefactos & Ciclo Operativo

Ecosistema de artefactos que articula el flujo de construcción, distribución y ejecución de software:

  • Imagen Docker: Plantilla inmutable de solo lectura construida por capas superpuestas (layers). Contiene el código de la aplicación, binarios del runtime, variables de entorno predeterminadas y dependencias. Se define formalmente mediante un archivo de instrucciones Dockerfile.
  • Contenedor: Instancia activa en ejecución de una imagen. Al inicializarse, Docker agrega una capa superior de lectura/escritura (writable layer) donde el proceso realiza modificaciones temporales en memoria o disco. Una única imagen puede respaldar múltiples contenedores concurrentes idénticos.
  • Registro (Registry): Repositorio centralizado o distribuido para catalogar y compartir imágenes (ej. Docker Hub, GitHub Container Registry). Permite versionar mediante etiquetas (tags como :latest o :1.0.0).
  • Ciclo completo y comandos canónicos:
    Dockerfile ──(docker build)──► Imagen ──(docker push/pull)──► Registry ──(docker run)──► Contenedor

    Comandos clave: docker build -t app ., docker run -d -p 8080:8080 -v volumen:/data --name mi-app app, docker ps, docker logs -f [id], docker exec -it [id] sh, docker stop y docker rm.

27. Dockerfile multi-etapa para Spring Boot Optimización de Builds & Seguridad

Patrón de empaquetado que divide el proceso de construcción en fases secuenciales para generar imágenes de producción mínimas, livianas y seguras:

  • Etapa de compilación (Builder): Utiliza una imagen pesada con el JDK completo y Maven/Gradle para compilar el proyecto y empaquetar el ejecutable .jar.
  • Etapa de ejecución (Runtime): Descarta las herramientas de compilación y parte de una imagen base limpia que solo contiene el JRE liviano (ej. eclipse-temurin:17-jre-alpine), copiando exclusivamente el .jar generado en la fase previa.
  • Aprovechamiento de la caché de capas: Copiar el archivo pom.xml y ejecutar la descarga de dependencias (mvn dependency:go-offline) antes de copiar el código fuente. Esto previene que Docker vuelva a descargar todas las librerías en cada modificación menor de código.
  • Ejecución como usuario sin privilegios: Por defecto, los contenedores ejecutan sus procesos como root. Definir un usuario y grupo acotado del sistema operativo (RUN addgroup -S app && adduser -S app -G app) limita drásticamente la superficie de ataque en caso de vulnerabilidades.
  • Archivo .dockerignore: Excluye archivos innecesarios o sensibles (target, .git, .env, node_modules), reduciendo el tamaño del contexto de build enviado al daemon y previniendo la fuga de credenciales.
28. Volúmenes y persistencia de datos Gestión de Estado

Por diseño, el almacenamiento dentro de un contenedor es efímero: toda información escrita sobre la capa superior se destruye irrevocablemente al detener y eliminar el contenedor (docker rm). La persistencia exige desacoplar los datos hacia el host:

Volúmenes Nombrados (Named Volumes):
Áreas de almacenamiento creadas y administradas íntegramente por el motor de Docker en rutas protegidas del host (ej. postgres_data:/var/lib/postgresql/data). Es el estándar obligatorio para bases de datos relacionales y NoSQL por su rendimiento y seguridad.
Montajes Vinculados (Bind Mounts):
Mapean un directorio o archivo específico y explícito de la máquina anfitriona hacia el contenedor (ej. ./uploads:/app/uploads). Permiten sincronización bidireccional inmediata, resultando altamente útiles en entornos de desarrollo local.

Comando Compose: docker compose down detiene y destruye los contenedores preservando intactos los volúmenes; la bandera docker compose down -v elimina deliberadamente los volúmenes asociados.

29. Redes en Docker y el error de localhost Resolución DNS Interna

El error de conexión más frecuente en entornos contenerizados radica en configurar la dirección localhost o 127.0.0.1 en la cadena de conexión de una API para alcanzar la base de datos:

  • Aislamiento de la interfaz loopback: Dentro de un contenedor, localhost apunta estrictamente a su propia pila de red aislada, no al sistema operativo del host ni a otros contenedores. Al intentar conectar con localhost:5432, la API busca el motor de base de datos dentro de su propio contenedor, arrojando Connection refused.
  • Redes virtuales de Docker Compose: Al iniciar un entorno, Compose crea una red puente (bridge network) privada compartida. En esta red opera un servidor DNS interno que asocia automáticamente el nombre del servicio definido en el archivo YAML con su dirección IP dinámica.
  • Reglas de resolución según el origen:
    • Contenedor API ➔ Contenedor Base de Datos: Se utiliza el nombre del servicio de Compose y el puerto interno no mapeado (ej. jdbc:postgresql://db:5432/mi_base).
    • Herramientas del Host (DBeaver/Navicat) ➔ Contenedor Base: Se utiliza localhost y el puerto publicado expuesto a la máquina anfitriona (el lado izquierdo de ports: "5433:5432").
    • Navegador Web ➔ Contenedor API: Se utiliza localhost:8080 (el navegador se ejecuta en el host).
    • Contenedor ➔ Servicio local corriendo en el Host: Se utiliza el hostname especial host.docker.internal.
30. Docker Compose: API + base de datos Orquestación de Servicios

Herramienta declarativa que permite definir, configurar y levantar arquitecturas compuestas por múltiples contenedores interrelacionados mediante un único archivo de configuración docker-compose.yml y un comando unificado (docker compose up -d):

  • Bloque services: Declara los componentes del sistema (ej. api y db). Cada servicio especifica su origen mediante construcción local (build: .) o descarga desde registro (image: postgres:15-alpine).
  • Mapeo de puertos (ports): Notación "host:contenedor" que expone puertos al exterior.
  • Inyección de entorno (environment / env_file): Parametriza credenciales y URLs sin modificarlas en el código.
  • Mecanismo de sincronización con healthcheck: La directiva tradicional depends_on solo espera a que el contenedor secundario se inicie, no a que el motor de base de datos termine su proceso interno de arranque. Configurar un healthcheck en la base permite condicionar el inicio de la API a su disponibilidad operativa real: 
    depends_on:
  db:
    condition: service_healthy
31. Configuración externalizada, variables y secretos Metodología 12-Factor App

Principio arquitectónico que estipula que una imagen Docker debe construirse una sola vez y permanecer estrictamente agnóstica al entorno, adaptando su comportamiento mediante variables de configuración externas:

  • Placeholders en Spring Boot: En application.properties o application.yml se declaran sustitutos con valores de respaldo predeterminados para desarrollo:
    spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/mibase}
  • Archivos .env vs. .env.example:
    • .env: Contiene credenciales operativas, contraseñas y claves criptográficas reales. Debe incluirse obligatoriamente en .gitignore y .dockerignore para impedir su exposición en repositorios.
    • .env.example: Plantilla versionada en el repositorio que documenta todas las variables requeridas por el sistema con valores ficticios de muestra.
  • Gestión de secretos: Las claves JWT y credenciales de acceso a bases de datos jamás deben hardcodearse en el código fuente ni quedar horneadas dentro de las capas de una imagen Docker. Si un secreto se filtra en un commit, debe considerarse comprometido y rotarse de inmediato.
32. Contenerización del sistema completo Topología Multicapa

Diseño e integración de un ecosistema desacoplado donde cada componente asume una única responsabilidad técnica:

  • Topología modular: Se levantan contenedores independientes para el frontend web, la API backend de Spring Boot, la base de datos relacional (PostgreSQL/MySQL) y el motor documental (MongoDB), interconectados sobre una red interna común.
  • Contenerización de Frontend SPA (React): Se implementa un Dockerfile multi-etapa donde una primera imagen con Node.js compila los recursos estáticos (npm run build), y una segunda etapa basada en un servidor Nginx ultraliviano (Alpine) sirve los archivos estáticos generados y gestiona el enrutamiento del lado del cliente.
  • Límites de comunicación: En una arquitectura SPA, el navegador del usuario final es quien consume la API. Por lo tanto, las URLs de los endpoints configuradas en React apuntan a los puertos publicados en el host expuestos hacia el navegador, mientras que la API y las bases se comunican privadamente por los nombres internos de servicio.
